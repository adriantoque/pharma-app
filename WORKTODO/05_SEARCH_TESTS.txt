--------------------------------------------------------------------------------
THE ONE PRODUCTION FACT THAT MATTERS
--------------------------------------------------------------------------------
DashboardScreen has no `repository` parameter. It reads
`context.watch<MedicineProvider>()`, and MedicineProvider reads nothing until
`auth.user != null` (medicine_provider.dart:100-108). Its constructor calls
`_onAuthChanged()` immediately, so the ORDER of login and construction is
load-bearing (convention C5).

    sign in  ->  construct MedicineProvider  ->  pumpWidget

Construct the provider before signing in and the catalogue never arrives, and
every test sees an empty price list and fails in a way that looks like a
filtering bug. This is the single most likely way to get this task wrong.

      and pump:

          Future<void> pumpHome(WidgetTester tester, {String query = ''}) async {
            tester.view.physicalSize = phoneSize;
            tester.view.devicePixelRatio = 1.0;
            addTearDown(tester.view.reset);

            final order = OrderProvider();
            addTearDown(order.dispose);
            final catalogue =
                MedicineProvider(auth: auth, storeFor: (_) => store);

            await tester.pumpWidget(
              ChangeNotifierProvider<OrderProvider>.value(
                value: order,
                child: ChangeNotifierProvider<MedicineProvider>.value(
                  value: catalogue,
                  child: const MaterialApp(home: DashboardScreen()),
                ),
              ),
            );
            await tester.pumpAndSettle();

            if (query.isNotEmpty) {
              await tester.enterText(find.byType(TextField), query);
              await tester.pumpAndSettle();
            }
          }

      Notes on the shape:
        - Keep the existing 360x720 physicalSize / devicePixelRatio 1.0 setup.
          Every narrow-phone assertion in this file depends on it, and the new
          destination labels are wider than the old ones.
        - `const StaticMedicineRepository().all()` is the fixed 64-item
          catalogue. Same trick nav_alignment_test.dart:36 uses.
        - `pumpAndSettle` after pumpWidget is required, because the catalogue
          arrives as a stream event, not synchronously.
        - Disposing the provider: `addTearDown(catalogue.dispose)`.

  [ ] Every `await pumpSearch(tester);` becomes `await pumpHome(tester);`, or

CHECKLIST -- the two that need real thought
--------------------------------------------------------------------------------
  [ ] Line 42, `renders the full list on a 360x720 phone`.

      This test has no equivalent any more, and pretending otherwise would
      produce a test that passes without meaning anything. On Home you CANNOT
      browse without typing -- that is the screen's whole design. "The full
      list renders" is not a reachable state.

      DECIDED (D2): split it into two.

        a) The browse state. Pump with no query. Assert what Home actually shows
           when nobody is searching: the count line reads "64 items" (it is
           outside the flex, so it is present), the tiles are there, and NO
           result rows are built.

        b) Rows behind a query. Pump with a broad query, assert the first
           alphabetic entry and that prices are formatted rather than raw
           centavos. The original also asserted
           `expect(find.text('₱65.00'), findsWidgets);` -- keep that, it is the
           "prices are formatted" check and it is the part of the test that
           still means something.

      Name the two parts so it is obvious which is which.

  [ ] Line 64, `changing the query returns the list to the top`.

      Two problems, both caused by the flex:

        a) It flings `find.byType(ListView)` to reach 'vicks'. On an EMPTY query
           that finder matches TWO lists -- the zero-height results list and the
           tiles list -- and `tester.fling` on a multi-match finder THROWS. It
           would not fail the assertion, it would blow up the test in a way that
           looks like a framework bug.

        b) The test needs a long enough list to actually scroll to the bottom
           before typing. With no query there is no scrolling list.

      Fix: give it a broad initial query that still contains 'vicks', so there
      is a real list with real length, THEN change the query and assert the
      reset:

          await pumpHome(tester, query: 'v');
          await tester.fling(find.byType(ListView), const Offset(0, -4000), 4000);
          await tester.pumpAndSettle();
          expect(find.text('vicks'), findsOneWidget);

          await tester.enterText(find.byType(TextField), 'a');
          await tester.pumpAndSettle();

          expect(find.text('Alcohol'), findsOneWidget);
          expect(find.text('vicks'), findsNothing);

      The comment at lines 68-70 explains WHY a broad query is used ("so the
      list does not shrink below the viewport and clamp the offset by
      accident"). That reasoning still applies and should be kept.

      Also check line 365-368, which does
      `find.descendant(of: find.byType(ListView), matching: ...)`. That one is
      inside the longest-name test, which already has a query, so it is safe --
      but verify it rather than assuming.
